# AI services

Live checks exercise the streamed inference path used by automatic replies. The model matrix records attempt counts, token usage and thinking length in `backend/build/reports/model-quality.json`. The separate streaming check writes `streaming-quality.json` with loading, prompt and total durations, throughput and requested thinking mode. Both honor `TIHO_TEST_MODELS`; all messages are synthetic and nothing is sent to Telegram.

DeepSeek R1 retains an explicit reasoning mode and a separate token allowance. [Thinking controls vary by installed model and template](https://docs.ollama.com/capabilities/thinking); an installed R1 8B emitted a thinking stream even with `think: false` during live validation. The application preserves its reasoning budget rather than assuming that flag always disables reasoning. Thinking output is audited separately and never used as the delivered reply.

DeepSeek R1 temperature is constrained to 0.5–0.7, following the [official R1 recommendations](https://github.com/deepseek-ai/DeepSeek-R1#usage-recommendations). Other model families retain their temperature settings. Application instructions use Spring AI's system role; every Telegram history record uses the user role, including the owner's earlier messages. Sampling defaults (`top_p`, `top_k`, repetition penalty) come from the installed model instead of a shared override. Events record the actual request. The prompt places learned voice and memory before the selected conversation tone and explicitly gives that tone priority.

Aigram uses [Spring AI 2.0](https://docs.spring.io/spring-ai/reference/api/chat/ollama-chat.html) as the local inference integration. Spring Boot constructs the services with constructor injection. The lifecycle remains explicit; creating the context does not log into Telegram or start inference.

| Component | Responsibility |
| --- | --- |
| `ConversationService` | Coordinate research, owner style, long-term facts and a bounded retry for required factual values. |
| `PromptBuilder` | Build system instructions and author-labelled user records; use Spring AI `MessageWindowChatMemory` for the recent conversation window. |
| `ChatCompletionService` | Call Spring AI `ChatModel`, apply inference options, request structured JSON and save actual measurements. |
| `ModelReplyReader` | Read the final response and durations from Spring AI. Use its `ThinkingTagCleaner` for legacy inline reasoning; never use separate thinking as an answer. |
| `ResearchFactGuard` | Compare required currency values with the final text, accepting equivalent decimal formatting and rejecting rounded or missing values. |
| `OllamaRuntime` | List, preload, download, cancel and unload local models. It does not generate conversation replies. |
| `MemoryCoordinator` and `MemoryProcessor` | Incrementally summarize changed history into the existing Markdown memory bank. |

The conversation window is rebuilt from actual Telegram history for each request, so failed previews, failed deliveries and cancelled generations do not enter the next conversation. Each history record is a JSON envelope with `username`, `name`, `message`, and `timestamp` fields. Additional `senderId`, `owner`, `automated`, and `messageId` fields distinguish contacts, genuine owner messages, and known automatic replies. Telegram's outgoing direction determines `owner`; names and handles do not establish identity. Unknown names, handles, and times remain empty rather than being invented. Timestamps use UTC ISO 8601. Quotes retain their message references in separate fields. All these records use the `user` role; only actual application instructions use `system`. The system instructions treat envelope values and quoted text as conversation data, require an answer to the latest incoming message unless a separate system task applies, and forbid copying transport metadata into the reply. The library's short-term memory does not replace the archive or editable `MEMORY.md` files. Known automated replies remain excluded from the owner's writing samples and shared owner facts.

Currency quotes carry explicit required values from the provider. A mismatch triggers one quality retry with those values; repeated inaccuracies become an explicit error before sending. URL and date fragments cannot satisfy a required quote. Explicit recall requests may reuse earlier facts.

`PersonalStyleBuilder` reduces genuine owner messages to optional punctuation and vocabulary observations. Literal examples from unrelated topics are not added to generation prompts: live testing showed that small models could copy their meaning instead of answering the question. Shared owner memory supplies facts and substantive preferences, not writing instructions. `SettingsStore` resolves named styles into a transient runtime field; `PromptBuilder` places the selected built-in or named style in a separate final system block. The selected style remains the final tone instruction. There is no phrase-repetition or natural-language analysis classifier.

Spring AI exposes native Ollama `thinking` and OpenAI-compatible `reasoning_content` / `reasoning` separately from final content. `ModelResponseStream` and `ModelReplyReader` preserve those typed reasoning fields for event details while returning only final content as the reply. Thinking-only responses remain empty-answer errors; thinking is never substituted for missing content. The SDK also removes supported legacy inline thinking tags. If a provider places unmarked reasoning in its normal content field, the application cannot reliably distinguish it from an intentional reply and does not guess from its wording. Use a model/provider template that exposes reasoning separately when that distinction is required.

`ModelResponseStream` aggregates final text and thinking independently for automatic replies, drafts, research planning and memory summaries. It has no total three-minute deadline: each received chunk resets a ten-minute inactivity watchdog, including chunks containing only thinking. A stalled stream fails explicitly, and cancellation still interrupts it. All generation uses the same streaming path even without an event trace, so background work cannot bypass the watchdog. Model warmup allows thirty minutes. The diagnostic quality matrix retains its own bounded per-case deadline; that test limit is not an application reply limit.

`ModelInfo.supportsAutomation` distinguishes manual drafts from automatic sending. A known unsuitable model (`qwen3:0.6b` in this release) remains available for previews. Settings, conversation rules and `PersonalReplyGenerator` enforce the restriction before inference, including legacy saved rules.

Source-only follow-ups may omit previously quoted rates; if a rate is included, it must remain exact. A combined request for the rate and source still requires the quote. Live provider tests use the same local clock as the production Spring configuration, including across midnight.

Owned engine shutdown snapshots child process handles before stopping the server, then forces remaining captured children to stop even if their parent has exited. A regression test covers the orphan-process race found during live checks.

Model options live in `backend/src/main/resources/models/inference.json`, independent of prompts and language packs. Thinking-only tags such as the current `qwen3:4b` use an explicit thinking channel and an extra token allowance; turning thinking off is not supported by that model. Hybrid tags can disable it. A response stopped by its token limit gets at most one larger-budget retry. Empty or still-incomplete final responses remain explicit errors, and separate thinking is never substituted for the final answer. No model is downloaded or substituted automatically.

The model catalog's maximum context capacities and the inference working window are distinct. Automatic budgeting and explicit per-model context settings are described in [token budgets](prompts-en.md). Local measurements use Ollama's actual total/evaluation durations and token counts; the application does not invent speeds for untested models. Measurements are stored in `model-measurements.json` inside the local profile.

Changing the global model affects conversations using `useDefaultModel`. A per-chat choice explicitly disables inheritance; choosing “Default” restores it. Existing rules without this flag follow the global model, removing the previous stale-model behavior.

Tests cover the Spring dependency graph, typed roles and history limits, structured search planning, response extraction, thinking controls, bounded reasoning retries, measurement persistence and download cancellation. Optional live tests use synthetic messages against installed models and public search sources; they send nothing to Telegram.

`LiveModelQualityTest` runs 20 scenarios on every installed model: 14 conversation, context and factual cases, plus the six built-in writing styles. External facts in this matrix are deterministic fixtures; inference uses the actual local models. Style checks use the same incoming message and a conflicting learned lowercase voice; the business style must retain formal writing. These checks cover observable properties and still require manual review of tone. Results are checkpointed to `backend/build/reports/model-quality.json`, including failures instead of stopping at the first model. Each case has a three-minute deadline, and models are unloaded between groups. Independent live-internet tests exercise real providers. Set `TIHO_LIVE_AI=true` to run the model matrix; `TIHO_TEST_MODELS` and `TIHO_TEST_CASES` restrict diagnostic reruns to comma-separated installed tags and case IDs.
